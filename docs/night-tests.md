## 1. ~~Распад accept по аптайму~~ — СНЯТО 17.09

Риск был в том, что мы унаследовали от профиля Pennyroyal
`--mamba-track-interval 64`, а в обсуждении RadixArk #8 именно это значение вместе с
короткими запросами названо триггером сползания accept почти к нулю за сутки аптайма.

**Сейчас стоит 256** — то же, что у прежнего форка, на котором за 27-часовое окно
распада не было (час 0 → 2.15, час 27 → 2.25). Риск неактуален.

Монитор оставлен на случай, если скорость однажды просядет без ошибок в логе:

```bash
cd /home/molochko/vllm && python3 _uptime.py penny
```

Разбивает accept и скорость по часам аптайма и выносит вердикт по сдвигу между
первыми и последними двумя часами. Осмысленно после 6+ часов работы.

## 2а. Префил и префикс-кеш — замер добавлен 17.09

Оказался полезнее decode-замера: `_night.py` меряет **только декод** и про префил не
говорит ничего.

```bash
cd /home/molochko/vllm && python3 _prefill.py "метка"
```

Шлёт промпт ~25k токенов с `max_tokens=1`, то есть меряет практически TTFT: трижды с
уникальным префиксом (холодный) и трижды повторно (тёплый).

Снятое 17.09: холодный **1.89 с (13 245 ток/с)**, тёплый **0.15 с**, выигрыш **12.6×**,
из промпта 24 960 токенов берутся из кеша. От числа слотов Mamba не зависит — при 48 и
256 цифры совпали. Это и есть главный рычаг для работы «прогнать модель по одному коду
несколько раз», и держится он на HiCache с радикс-кешем.

## 3. Вырождение в длинных рассуждениях — требует простоя

**Вопрос.** В обсуждении RadixArk #3 описан срыв в неостановимый повтор при
длинных рассуждениях и многократных вызовах инструментов, в конфигурации почти
совпадающей с нашей. Участник треда показывает, что при выключенном спекулятиве
срывы исчезают, то есть дело в тракте draft-verify. У нас это не воспроизведено и
не опровергнуто.

**Со спекулятивом (простоя нет):**

```bash
cd /home/molochko/vllm && DEGEN_MAXTOK=32768 python3 _degen.py "спекулятив ВКЛ" 3 | tee _degen_on.log
```

**Без спекулятива (простой ~5 минут на переключение):**

```bash
cd /home/molochko/penny
cp tp2-serve-flash-next.sh tp2-serve-flash-next.sh.bak
sed -i 's/^\s*--speculative-[a-z-]*.*\\$//' tp2-serve-flash-next.sh
sudo systemctl restart sglang
# дождаться готовности:
until curl -skf -m 4 https://127.0.0.1:1234/health >/dev/null; do sleep 10; done
cd /home/molochko/vllm && DEGEN_MAXTOK=32768 python3 _degen.py "спекулятив ВЫКЛ" 3 | tee _degen_off.log
# вернуть:
cp /home/molochko/penny/tp2-serve-flash-next.sh.bak /home/molochko/penny/tp2-serve-flash-next.sh
sudo systemctl restart sglang
rm -f /home/molochko/vllm/.maintenance
```

**Что смотреть.** Строку `ИТОГ: N вырождений из M` в обоих логах. Проба помечает
прогон как вырождение при цепочке от 40 одинаковых символов подряд или от 8
повторов одной n-граммы. Считает и `reasoning_content`, и `content` — первая версия
пробы этого не делала и намеряла пустоту.

**Вердикт:** срывы есть со спекулятивом и нет без него → подтверждается диагноз из
#3, и это уже вопрос качества, а не скорости.

## 4. mem-fraction 0.88 → 0.90 — последним, если вообще

**Вопрос.** Даёт +1.9 ГБ бюджета, примерно +280k токенов KV (+12%). Но забирает их
из запаса под префил: сейчас движок оставляет 9.85 ГБ, останется ~7.9, а длинный
префил требует **сверх статики около 4.4 ГиБ**, и на двух одновременных это уже
впритык. В старой таблице notes против 0.90 написано «пик у потолка, падает на
2 агентах» — но мерялось это на прежней сборке, без online MXFP8, который ужал веса
примерно на 3.6 ГиБ. Может и перенестись, а может и нет.

```bash
sed -i 's/--mem-fraction-static 0.88/--mem-fraction-static 0.90/' \
  /home/molochko/penny/tp2-serve-flash-next.sh
sudo systemctl restart sglang
```

**Проверять длиной контекста, а не числом коротких запросов.** Это записанный в
notes промах, повторённый дважды: «проверял параметры памяти числом потоков на
коротких промптах, а ломалось длиной». Нужен длинный контекст на 2+ агентах —
`_load.py` даёт ~20k промпт, для настоящей проверки надо больше; ориентир из старых
замеров: 739k одним запросом и 663k на четырёх.

Откат — тем же sed обратно на 0.88.
