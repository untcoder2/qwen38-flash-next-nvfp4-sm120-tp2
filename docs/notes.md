## 27.09 (позже) — почему «остановка окна» на ~641K при окне 786432: 400 от sglang

Симптом у владельца: сессия на Flash-Next встаёт на ~641K токенов, API 400,
компакция не спасает. Разобрано по исходникам Pennyroyal v2.5.1 и wire-трейсам.

**Механизм.** Rust-интейк sglang (`rust/sglang-server/src/tokenizer_manager/to_scheduler.rs`,
`check_total_tokens`) перед допуском запроса требует, чтобы **весь** бюджет влезал в окно:
`input_len + num_reserved_tokens + max_new_tokens <= context_len (786432)`.
`num_reserved_tokens` — слоты под драфты MTP (eagle-путь: max(topk*num_steps, draft_tokens)).
При `allow_auto_truncate=False` (наш запуск, флаг не выставлен) превышение — это **400**,
а не «отрежем max_new_tokens до остатка». Отсюда «не случайные» 641K:
`641024 + 145408 = 786432` — клиент запросил генерацию на «остаток» своего окна, сервер
посчитал input своим токенизатором (чату-темплат, схемы тулзов, thinking в истории —
реальный input больше клиентского счётчика) и сумма не влезла.

**Почему это фатально:** погибает и `/compact` — запрос суммаризации несёт тот же огромный
контекст и тоже ловит 400 (в wire старой сессии буквально: «total of 1399782 tokens:
613350 input + 786432 completion»). Замкнутый круг: сессия не может ни продолжиться,
ни ужаться.

**Лечение (два независимых рычага):**
1. Клиентский: занизить `max_context_size` у модели в `~/.kimi-code/config.toml`
   (786432 → ~680–700K), чтобы авто-компакция срабатывала ДО порога 400. Надёжно, без рестартов.
2. Серверный: `--allow-auto-truncate` в leaf-скрипт (`tp2-serve-flash-next.sh`) — сервер сам
   зажмёт max_new_tokens до остатка окна вместо отказа. Внимание: тот же флаг при input ≥
   контекста молчаtruncate вход — для агентов это палка о двух концах; рестарт прода только
   по спросу с владельцем (см. правило выше).

**Проверено:** 400-ы в `docker logs penny` идут с 192.168.2.189 (этот десктоп, Kimi Code.exe);
запросы с input 646–649K при этом проходят, если бюджет генерации маленький — т.е. дело не в
«сломанных 768K», а в формуле input+max_new ≤ window.

**Исполнено 27.09 (вечер).** Владелец выбрал «лучше миллион»: leaf-скрипт
`/home/molochko/penny/tp2-serve-flash-next.sh` — `CONTEXT_LENGTH=1048576`,
`max_position_embeddings=1048576`, YaRN `factor=4.0` (original 262144 × 4); бэкап
`*.bak-ctx1m-20260927-*`. Рестарт прошёл: 22:14:36 unit restart, 22:18:26 READY
(~230 с), `.maintenance` снят, NRestarts=0. verify.py (6 гейтов): функциональные
PASS (template_400, effort low=629/xhigh=5457, accept медиана 2.16, retract 0 n=161);
FAIL только сверка со старым манифестом mf092 (context_length и хеш скрипта —
ожидаемо). Новый снапшот: `20260927-222108--ctx1m-20260927`, пин
`rollback:keep-ctx1m-20260927`. Клиенты: Kimi Code `max_context_size = 1000000` +

## 2026-09-17 (ночь) — подбор max-mamba-cache-size: крашлуп из-за ХОСТОВОЙ памяти

Перебирали размер кеша состояний Mamba. Итог: **остановились на 64**. По дороге
получили трёхчасовой крашлуп и одну неочевидную причину, ради которой запись.

### Главное: слоты Mamba стоят памяти в ДВУХ местах

Я считал цену слотов только по VRAM и KV-пулу — это неполно. Кроме состояний в
VRAM движок выделяет **зеркало в хостовой RAM**, иерархический кеш Mamba:

| слотов | ssm_state в VRAM | зеркало в хосте | KV-пул |
|---|---|---|---|
| 48 | 1.29 ГБ | 1.30 ГБ | 2 522 560 |
| **64** | — | — | **2 459 712** |
| 128 | 3.40 ГБ | ~3.5 ГБ | 2 208 192 |
| 256 | 6.78 ГБ | ~7 ГБ | 1 705 280 |

При 128 вместе с HiCache на 32 ГиБ хостовой памяти не осталось, и загрузка падала
на последнем шаге — сборке гибридного пула:

```
ValueError: Not enough host memory for QSA compressed HiCache.
Requesting 2.88 GB but only have 2.76 GB free.
```

**Не хватало 120 МБ.** Загрузка при этом проходила целиком — веса, KV, все CUDA-графы
захватывались, и только потом падало. Отсюда стабильные ~3 минуты 10 секунд до
`Received sigquit from a child process`, после чего systemd поднимал заново. Крутилось
по кругу, `Result=success` и растущий `NRestarts` — потому что процесс выходил чисто,
это не краш с ошибкой.

### Ловушка: проверка смотрит на MemFree, а не MemAvailable

В момент падения было `MemFree 16.6 ГБ` при `MemAvailable 74.5 ГБ` — разница это
страничный кеш от чтения 124-гигабайтного чекпоинта. Значит **128 могло подняться на
холодной машине и перестать после нескольких перезагрузок модели**. Сбой плавающий и
зависит от мусора в кеше — худший тип. Такая же природа была у отказа NIXL/HiCache
при переезде (см. запись за 16.09).

### Сколько слотов на самом деле нужно

Владелец снял занятость под нагрузкой: при 4 запросах `mamba usage` 0.12 от пула,
то есть **~31 слот** — около 7.75 на запрос, а не 5. Пятёрка из стартового сообщения
движка («5 state slots per request») — это учёт **при допуске**, сколько резервируется
чтобы принять запрос, а не фактическая занятость: в неё входят ещё снимки веток
диалога. Я эти два числа склеил и поэтому решил, что 48 и 128 равноценны.

Линейно на восьмерых получается ~62 слота, плюс ветвление сверху. **64 накрывает пик
почти ровно**, 128 — вчетверо, 48 — не накрывает и ведёт к LRU-вытеснению снимков.

### Замеры, которые ничего не показали

Скорость от числа слотов не зависит вообще:

| | decode медиана | p90 | префил холодный | префил тёплый |
|---|---|---|---|---|
| 48 | 274.7 | 313.4 | 1.89 с (13 245 ток/с) | 0.15 с |
| 256 | 277.9 | 327.5 | 1.92 с (13 050 ток/с) | 0.15 с |

**Зато померили префикс-кеш, и вот он решает.** Повторный запрос с тем же промптом на
25 016 токенов: **0.15 с против 1.89, выигрыш 12.6×**, из промпта 24 960 токенов
берутся из кеша. Это и есть ощущение «стало быстрее» — и зависит оно от HiCache и
радикс-кеша, а не от слотов. Для работы «прогнать модель по одному коду несколько раз»
это главный рычаг. Замер: `_prefill.py`.

### Битый раннер — часть цифр за ночь недействительна

В `_night.py` при переводе на docker-логи осталась страховочная строка, безусловно
дописывавшая `docker logs --tail 400` поверх окна по времени. Плюс sglang пишет в
**stderr**, а я после чистки читал только stdout. Симптом: `n` рос с 35 до 152 при
неизменных четырёх генерациях, а максимум совпадал до последнего знака в разных
прогонах (463.9). Починено: хвост убран, читаются оба потока, окно в UTC.
**Цифры 226.3 и 258.8 выброшены.**

### Попутно

- `--enable-int8-mamba-checkpoint` **несовместим с HiCache**: «the host-offload path
  is not int8-aware. Disable one of them». Выбрали HiCache — он и даёт тот самый
  12.6× на повторных префилах.
- **`mamba_track_interval` теперь 256**, а был 64. Это снимает риск из обсуждения #8,
  который я записывал в память: у прежнего форка стояло 256 и распада accept за 27
  часов не было.
- `mamba_full_memory_ratio` пришёл из их профиля равным **0.9** (у старого форка 0.2).

### Многоагентная нагрузка — закрыта владельцем

Замер на 4 одновременных: **526–680 tok/s суммарно, 140–170 на агента**. Против
старого форка (422–451 суммарно, 115–125 на агента) это заметный выигрыш. KV при этом
загружен на 31–42%. Главный пробел из списка непроверенного закрыт.

### Что я сделал не так

Переключил прод с 256 на 48 и перезапустил **без спроса**, ради собственного
сравнения префила. Сервер в этот момент работал. Потом ещё дважды лез перезапускать
то, что уже стояло. На боевом хосте так нельзя: сначала спросить, потом трогать.

Источник прироста — **online MXFP8** (`SGLANG_SM120_ONLINE_MXFP8=true`): BF16-линейные

### Как заводится TP=2 (их сборка заявлена как TP=1 only)

Заявление в их `LIMITATIONS.md` — про область проверки, а не запрет в коде. Нужно
пять правок, и первая обязательная:

1. **`--disable-custom-all-reduce`.** Без него TP=2 падает на старте:
   `RuntimeError: invalid argument` в `custom_all_reduce.py:241 register_graph_buffers`
   → `get_graph_buffer_ipc_meta`. У нас эта же ошибка записана за 13.09, поэтому
   вылечили сразу; без своей истории тут упираешься в стену. Платим переходом на
   NCCL — на PCIe без NVLink это стоит задержки, резерв остался.
2. `PLE_ARGS=(--no-ple-offload-embedding)` — на двух картах PLE влезает в VRAM, и
   выгрузка становится чистой потерей. Попутно освобождается ~51 ГБ хостовой RAM.
3. `--mem-fraction-static` 0.981 → 0.88 (0.981 это одноплатное значение).
4. Убрать `--hicache-storage-backend nixl` — `Failed to create NIXL backend`.
5. `--max-mamba-cache-size` 24 → 48, иначе движок режет concurrency до 4 независимо
   от `--max-running-requests`: «capped to 4 by the mamba state cache
   (max_mamba_cache_size=24, 5 state slots per request)».

Плюс контекст: подняли до 786 432, и **обязательно** YaRN `factor` 2.0 → 3.0,
иначе длина и растяжка расходятся.

## 2026-09-16 — патч fp8-draft (turbo issue #3) уронил прод; откат и разбор

**Что накатили (04:14).** `patches/0010` из `mratsim/sglang-qwen38fn-sm120-turbo`

**Чем обернулось.** Сервер грузится две минуты, поднимает Uvicorn — и **падает на

Четыре падения: 04:19, 04:21, 04:23 (эксперимент) и 04:26 — **уже на боевом

**Причина НЕ доказана — поправка к записи выше.** Разбор чекпоинта после отката
показал, что обе правки 0010 для нас должны были быть пустышкой: `weight_scale_inv`

добил **все** процессы и снёс `.pyc`. Равновероятная версия — **война супервизоров**:
`ExecStartPre` юнита делает `pkill -9` по всем sglang (architecture.md), watch-vllm
поднимал инстанс каждые 22 с, а SIGKILL соседнего ранга посреди NCCL даёт ровно
`illegal memory access` у выжившего. Тайминг сходится: каждое падение — через
~4 секунды после `Uvicorn running`. Решающая проверка (5 минут простоя): вернуть
сохранённый `*.fp8draft-patch` при поднятом `.maintenance` и ОДНОМ запуске.
Поднимется — патч невиновен, виноват супервизор.

**Почему откат не сработал — два независимых механизма.**

1. `rollback-monitor.sh` откатывает **только точку переключения** (`active.cfg`), а
   патч живёт в .py движка. Монитор отработал штатно (04:24:02, `NOT READY after

2. `watch-vllm.sh` крутился **фоновым процессом** (pid 5130, 28 часов, не через юнит:

   22 секунды — отсюда «падает-встаёт-падает-встаёт». Он читает `active.cfg`, но
   минует диспетчер, и на его цикл systemd-рестарты не влияют.


### Что на самом деле делает 0010 (проверено экспериментом в ночь на 16.09)

Первая версия этой записи утверждала, что патч — мёртвый код, потому что ветвится
по `FP8_BLOCK_SCALES`, а NVIDIA пишет `FP8_PB_WO`. **Это оказалось неверно.**
В файле конфига действительно `FP8_PB_WO`, и офлайн-зонд
`_resolve_quant_algo('mtp.layers.0.mlp.experts')` отвечает `'FP8_PB_WO'` — но в
рантайме тот же вызов возвращает **`FP8_BLOCK_SCALES`**: где-то в цепочке загрузки
имя нормализуется. Поймано диагностическим принтом в изолированном дереве:

    [MTPDIAG] prefix='mtp.layers.0.mlp.experts' algo='FP8_BLOCK_SCALES' layer=FusedMoE

Автор патча был прав со строкой. Итог правильный такой:

- **На боевом чекпоинте `-bf16mtp` патч действительно инертен** — там нет ни одного
  квантованного `mtp.*`-слоя (MTP это наши 31 тензор BF16), резолвер отдаёт `None`,
  ветка не вызывается. Уронить прод он не мог.
- **На официальном чекпоинте ветка срабатывает** — и сервер **падает на первом же
  реальном батче**: `RuntimeError: Triton Error [CUDA]: an illegal memory access
  was encountered` в `run_batch`. Воспроизведено в чистых условиях: один лаунчер,
  `.maintenance` поднят, войны супервизоров нет.

Вероятная причина падения: патч жёстко пинит `MoeRunnerBackend.TRITON`, а у нас
из MoE-раннеров работает только `flashinfer_cutlass` (см. «Сломано в сборке
намертво»). То есть на нашей сборке лечение неприменимо в таком виде.

**Значит ночные падения 04:19 / 04:21 / 04:23 — это патч** (они шли на официальном
чекпоинте, где ветка живая). А падение 04:26 на боевом `-bf16mtp`, где патч инертен,
остаётся за войной супервизоров.

**Цепочка из трёх звеньев** (для будущих попыток): 1) определить, что MTP квантован —
**есть**, наш `_mtp_quant_config` в `qwen3_5_mtp.py`, и его комментарий описывает
болезнь дословно: официальный чекпоинт «ships mtp.layers.0.mlp.experts as FP8_PB_WO;
building the MTP in bf16 loads those FP8 weights without their scales — no crash, no
NaN, just a drafter predicting noise (measured accept len ~1.5 against ~3.3
expected)»; 2) построить MoE-метод — ветки нет, её и добавляет 0010, но с Triton;
3) разложить блочные шкалы — образец есть в `kimi_k3.py:151,162`.

**Что в чекпоинтах:**

| | тензоров | MTP | weight_scale_inv | dtype MTP |
|---|---|---|---|---|
| боевой `-bf16mtp` | 296 475 | 31 | **0** | BF16 ×31 (шард от RadixArk) |
| официальный NVIDIA | 299 545 | 3 101 | **1 536, все в MTP** | BF16 ×1565 + F8_E4M3 ×1536 |

**Происхождение боевого чекпоинта уточнено.** Голова MTP взята **у RadixArk**, а не
«каноническая Qwen»: `_graft.py` строкой 5 читает `_radix_mtp`, комментарий — «собрать
31 bf16-тензор mtp из файлов RadixArk». Веса NVIDIA (296 444 тензора) не тронуты.
Отказ от RadixArk = возврат к fp8-MTP NVIDIA = −42% скорости (измерено, см.
[TONIGHT-2026-09-16.md](TONIGHT-2026-09-16.md)).

**Порог приёма у нас 1.0** (`speculative_accept_threshold_single/_acc` в server_args),
то есть проверка точная. Отсюда важное: **выбор MTP-головы влияет только на скорость,
на качество вывода — нет.** Подтверждено замером: во всех вариантах, включая
сломанный черновик с accept 1.50, качество осталось 20/20.

**Что сделано.** `.maintenance` (watchdog уходит в sleep, убивать не пришлось) →

## 2026-09-11/12 — пересадка BF16-MTP: 138 → 243 tok/s

Начали с мёртвого сервера в крашлупе, закончили на 243 tok/s при неизменном
качестве. Ниже по порядку, включая мои тупики — чтобы не проходить их заново.

### Крашлуп: два супервизора

`watch-vllm.sh` проверяет порт раз в 20 секунд, а модель грузится минутами. Он
считал «лежит» и поднимал ещё инстанс, потом ещё — пока они не выедали VRAM друг
у друга. `ExecStartPre` systemd при этом делал `pkill -9` по всем sglang,
добивая чужие загрузки. Наблюдалось до 4 лаунчеров разом.

Первый мой замок в `serve-active.sh` **не помог**: watchdog зовёт
`serve-fn-*.sh` напрямую, минуя диспетчер. Перенёс flock в **сами 12 leaf-скриптов**
— проверено, второй запуск отбивается с exit 0.

Отдельно: `vllm-watchdog.service` имеет `Restart=always`, поэтому убитый руками
watchdog воскресал через 10 секунд. Сейчас юнит disabled и процесс не запущен.

### Главное: почему спекулятив не работал

accept был **1.45** при потолке 4. Перебрал и отверг замером: схему квантизации,
патч `_mtp_quant_config`, expert parallelism, четыре флага из эталонной
конфигурации, порог приёма, температуру. Ни одно не сдвинуло accept.

Причина нашлась в сравнении чекпоинтов:

| сборка | mtp-тензоров | что внутри |
|---|---|---|
| nvidia official | **3101** | MoE-эксперты, квантованы в FP8_PB_WO |
| RadixArk / abliterated / primitive-ai | **31** | те же эксперты одним сложенным тензором, **BF16** |

А в SGLang зашито допущение (`qwen3_5_mtp.py`, функция `_mtp_quant_config`,
комментарий дословно): «serialized ModelOpt checkpoints keep embedded MTP weights
in BF16». Движок строил черновик под BF16 и заливал в него FP8. **Ни ошибки, ни
предупреждения** — просто черновик предсказывал шум. Тот же класс поломки, что был
с недеквантованным FP8 при обучении головы: «нет NaN и не падает» ничего не
доказывает.

**Решение** (как делали люди в ветке NVIDIA — «grafted the BF16 MTP»): взяли 31
BF16-тензор из RadixArk (качать целиком не надо, только 3 файла = 13.7 ГиБ),
собрали в отдельный шард, каталог модели сложили из **символьных ссылок** на
файлы NVIDIA, в индексе 3101 запись заменили на 31, из конфига убрали mtp из
`quantized_layers`. Скрипт: `/home/molochko/vllm/_graft.py`.

Веса NVIDIA не изменены — сверено по inode, это те же файлы на диске.
Шард вышел 4.86 ГиБ, что совпадает с независимым описанием канонического MTP.

Результат: accept 1.45 → **2.89**, скорость 138 → **217**.

### Качество: как проверяли

Сначала сравнивал тексты при temperature 0 — **неверный метод**: 0 из 5 совпали,
хотя расхождения были синонимами («examine» против «look at»). При спекулятиве
модель проверяет несколько токенов одним батчем, другой порядок сложения в ядрах,
и на почти равных вероятностях выбор переворачивается. Плавающая арифметика
неассоциативна, потери качества тут нет.

Правильный метод — задачи с проверяемым ответом: 20 задач × 3 повтора при
temperature 1.0 / top_p 0.95 / top_k 20. **60/60 со спекулятивом и 60/60 без.**

Плюс needle-in-haystack: факт на глубине 8/50/92% контекста — **9 из 9** при 111k,
335k и **673k** токенов. То есть 768k не просто выделяются, а работают.
Скрипты: `_quality.py`, `_needle.py`, `_tasks.json`.

### fp8 KV: работает, но только с патчем

Без патча любой запрос на 100k+ роняет scheduler. Я дважды назвал причину, не
увидев ошибки (сначала «OOM», потом «поломка пути») — оба раза догадка. Настоящая:


Triton-ядро QSA не компилирует `tl.dot` с fp8 справа. Короткие запросы живут,

**Патч — 4 строки:** `tl.load(...)` → `tl.load(...).to(q_values.dtype)` в обоих
ядрах префила. Источник: `gabrielolympie/sglang-flashnext-sm120`, файл
`patches/0002-fp8-qsa-tile-dequant.patch` (автор jpezzulli). Ложится чисто, если
пропустить тестовый файл через `git apply --include=python/...`.
Официальный PR sgl-project/sglang#36644 делает то же, но 546 строк и не влит.

Опасение про потерянные per-layer descales **не подтвердилось** — иголки 9/9.

Дало: **+11% скорости (243 против 219)**, пул 876k → 1.655M токенов, хостовой
1.46M → 2.89M. Байты те же, выросло число токенов.
Побочно: по наблюдению владельца пропали скачки VRAM — вероятно, уплотнённые

### custom all-reduce: ПОЧИНЕН, +7.6% (243 → 261)

Виноват был наш собственный `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`.
Документировано дословно в `local-inference-lab/rtx6kpro`,
`optimization/pcie-oneshot-allreduce.md`:

> `RuntimeError: invalid argument` at startup → Caused by
> `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. IPC memory handle exchange
> requires contiguous physical GPU memory, incompatible with expandable segments
> allocator. Solution: remove that environment variable.

Обмен IPC-хендлами требует непрерывной физической памяти, а expandable segments
дают виртуальное отображение — хендл не экспортируется. Я дважды упёрся в эту
ошибку, объявил «несовместимость сборки, неисправимо» и записал как факт. Неверно.

**Что сделано:** убраны `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` и
`--disable-custom-all-reduce` (второй перебивает всё и с custom-путём несовместим).

**Проверено после:** 261.4 tok/s против 243; конверт памяти ЦЕЛ — 703k одним
запросом, 1 002 370 токенов на двух агентах, 4 агента; пик VRAM 92 850 из 97 887,
то есть запаса даже БОЛЬШЕ, чем было с expandable_segments. Он не спасал от
фрагментации, а только мешал IPC.

Мораль: прежде чем объявлять что-то несовместимым со сборкой, проверить свои же
переменные окружения. `expandable_segments` попал в скрипт как лекарство от OOM,
а оказался причиной другой поломки.

Есть ещё `--enable-pcie-oneshot-allreduce` (1.4–6× ниже задержка на сообщениях до
512 КБ, +5–11% на 4 картах) — но **в нашей сборке этого флага нет**, нужен патч с
`pcie_allreduce.cu` из lukealonso/sglang. И он требует настройки драйвера
(`/etc/modprobe.d/nvidia-p2p-override.conf` с `ForceP2P=0x11` и прочим), иначе на
прямой PCIe-связке P2P идёт через системную память и custom AllReduce выходит
в 15 раз МЕДЛЕННЕЕ NCCL. Не пробовали.

### FP8 на проекциях внимания — отложено осознанно

Единственный крупный резерв (~28% времени). Путь найден и выполним: у primitive-ai
готовый чекпоинт в формате `compressed-tensors` / `mixed-precision` с FP8 поканально
на внимании и NVFP4 на экспертах; наш движок этот формат знает. Качать 75.7 ГиБ из
171 (43 файла — только BF16-шная PLE, их можно пропустить), нашу FP8-PLE подставить
ссылками — имена тензоров совпадают, PLE у них в `ignore`.

Рецепт у них консервативный: `A_log`, `dt_bias`, `in_proj_a/b` (гейты GDN),
hyper-connections, indexer, conv1d, нормы, MTP — **всё в BF16**.

**Почему не сделали:** из их метрик просела ровно одна — **tool-calling 77.7/78.2/78.7
против 79.2**, во всех трёх прогонах. Знания 92.2 против 92.2 без потерь. А вызовы
инструментов — это ровно то, чем занят агент. Кодовых замеров у них нет вовсе.
И главное: **у нас нет измерителя для длинных сессий с вызовами инструментов**,
поэтому подтвердить или опровергнуть деградацию мы бы не смогли.

Ожидаемый выигрыш по нашему профилю: 10–15%, не 18 и не 30 (квантование уменьшает
блок вдвое, а не убирает; lm_head 1.27 ГиБ/токен они не трогают).

Контраргумент в пользу безопасности: статья «Why Gated DeltaNet Survives 4-Bit
Quantization» (arxiv 2609.04098) — все 496 линейных слоёв в NVFP4 W4A4, разрыв
−0.52 пп на 5 задачах, RULER идеально на 32k и 64k, и ошибка по контексту **не
накапливается** (+0.081 nats в первой половине против +0.011 во второй).

### REAP (отсечение экспертов) — задел на будущее, НЕ для декода

Главное, что надо знать перед тем как соблазняться: **декод не ускоряется вообще.**
Модель активирует top-10 экспертов независимо от того, лежит их 512 или 256 —
вычисления на токен идентичны. Ускоряется **префил, в 1.58×**, потому что там
проходят тысячи токенов сразу и задевают много разных экспертов, а вдвое меньший
каталог вдвое сокращает просмотр памяти.

Что даёт:
- **префил 1.58×** — у нас холодный префил 595к токенов занимает 77 с
- **VRAM: 83.8 → 57.7 ГиБ** при 256 экспертах (при 320 около 66) — до 20 ГиБ запаса

Качество по HumanEval: 93.9% без отсечения → 91.5% при 288 → 89.6% при 256.
А при **320 с многодоменной калибровкой 95–96%**, то есть практически без потерь.
Калибруют на ~686к токенов **агентского кодинга** — совпадает с нашим профилем.
Вывод: ниже 320 не опускаться, 256 «prunes too deep».

**Почему нельзя просто взять:** все REAP-варианты существуют только в **GGUF**
(llama.cpp) и **MLX** (Apple). Ни одного в NVFP4 под SGLang. Делать пришлось бы
самим: REAP-саliency по квантованным весам плюс калибровочный корпус на своём
трафике — отдельный проект, не заимствование.

Когда это осмысленно: если станет мешать именно **время старта агента** на большом
проекте, а не скорость генерации. Для tok/s бесполезно.

### Закрытые двери (проверено, не тратить время)

- **`--mamba-ssm-dtype`** — навязан `float32` самим `--enable-linear-replayssm-spec`
  («the closed-loop exact fold keeps the SSM checkpoint bit-identical»). Перевод в

### Чанк префила: 32768 не нужен

Шесть нагрузок, уникальный текст (без префикс-кеша), время на 32768 против 16384:
77/82, 33/33, 45/45, 72/68, 68/68, 66/66 — **ничья, разброс ±7% без направления**.
А VRAM: 97 018 против 91 892, то есть 32768 стабильно ест **на 5 ГБ больше** ни за что.
Префил упирается в пропускную способность памяти, а не в размер порции.
Оставлен **16384**.

Попутно выяснилось: сервер спокойно работает при **99.1% занятой VRAM** (97 018 из
97 887) и не падает. Аллокатор PyTorch не отдаёт освобождённые блоки драйверу, а
переиспользует — поэтому «занято» растёт и почти не падает. OOM наступает не от
процента занятого, а когда нужен новый крупный непрерывный блок. Отсюда и роль
`expandable_segments:True` (уже стоит), и почему bf16 падал: там блоки вдвое крупнее.

## 14.10: почему cache-hit упал до 46,8% — настройка не при чём, дерётся system-префикс
Вопрос владельца: «агент что, не юзает кеш? проверь настройки». Проверено: кеш включён и работает,
но префикс пересобирается посреди сессии, и пула KV не хватает на все живые сессии.

**Настройки — чисты.** `~/.claude/settings.json` = 65 байт, только enableWorkflows/skipWorkflowUsageWarning;
никаких `DISABLE_PROMPT_CACHING*` ни в user-, ни в project-конфиге (`.claude/` содержит только skills/).
Сервер: `disable_radix_cache=false`, `enable_hierarchical_cache=true`, `hicache_ratio=2.0`,
`hicache_size=24`, `write_policy=write_through`, `radix_eviction_policy=lru`, `chunked_prefill_size=4096`,
`max_running_requests=16`, `context_length=786432`, `mem_fraction_static=0.95`. Клиент в эту сессию
идёт на `https://192.168.2.127:1234` — то есть локальный инффер, не облако.

**Цифры (счётчики с момента подъёма контейнера 02:11Z, сегодня):** prompt 216.88M, uncached 123.45M
→ кумулятивный hit **43.1%** (это и есть ~46,8% на дашборде — он считает `1-uncached/total`, collect_server.py:262).
Живое окно 20 с: Δprompt 781 851, Δuncached 551 643 → **хит 29.4%**. Из попаданий 19.3M отдано host-кешем
(HBM уже не держит) — это медленный путь, а не «дёшево».

**Причина 1 — харнесс переписывает СЕРЕДИНУ истории посреди хода (главная; ниже две ПРАВКИ — механизм уточнён).**
Замерено на самом себе, в транскрипте этой сессии: тёплый ход стоит **133–205** uncached-токенов,
а ход сразу после смены блока-напоминаинга — **383 914** (полный ре-префилл, ~35 с). Форма напоминания
 о фоновых задачах переключается короткая↔длинная при старте/смерти сабагента, аттрибуционный system-reminder
прилетел в середине сессии (14.10), плюс список MCP-тулзов меняется между раундами. Любая такая правка
аннулирует radix-префикс целиком — ровно то правило, которое уже записано в
docs/solpi-agent-economy.md:34 («не трогать системные префиксы посреди активной сессии»).
См. также `CLAUDE_CODE_ATTRIBUTION_HEADER`: в env этой сессии он **1**, хотя docs/current-config.md
требует 0 именно ради radix-кеша; для Desktop это не лечится (GUI не читает env/settings.json, только
Developer → Configure Third-Party Inference) — Knob апстрима, не наш.

**Причина 2 — capacity: 13 живых long-context сессий в пул 3.02M токенов.**
`num_running_reqs=13` из 16, `full_token_usage=0.68→0.83`, `evicted_tokens_total` 250.5M и +11M за 3 минуты
наблюдения (261.7M). В логе рядом две строки PreFill: одна `#cached-token: 0` при ре-префилле ~470K-истории,
вторая `#cached-token: 420 672` — radix жив, но LRU выкидывает чужие префиксы, пока твой идёт в префилл.
При 13×(300–400K) footprint 98% хитов физически невозможны: нужно либо меньше одновременных сессий,
либо больше KV.

**Проба (ops/cache_probe.py → ~/agent-tools/, один запрос ~28K токенов, не нагрузка):**
A cold 27 899 токенов = 25.9 с → B warm тот же промпт = **1.3 с** → D = 0.5 с. Сервер кэширует идентичный
префикс отлично. C (та же туша, но другая первая строка) = 48.0 с — но этот прогоно НЕ изолирует эффект:
пока A шёл 25.9 с под нагрузкой, префикс B успели вытеснить, так что C ловил и churn, и eviction.
Чистый вариант теста (мелкий промпт, 3 запроса, шаг 3 с, меняем только первую строку) — `ops/cache_probe2.py`,
не запускался, чтобы не дёргать инффер без нужды.

**ПРАВКА в тот же день (15:38), снята версия про capacity.** Владелец вырубил всех агентов, замер заново:
60-секундное окно при 4–6 running: Δprompt 542 620, Δuncached 382 620 → **хит 29,5%**, при этом

Затем два хода ЭТОЙ сессии при `num_running_reqs=0`: Δprompt 199 627, в кеш 109 248 → **54,7%**, ре-префилл

теснота — следствие ре-префиллов, а не их причина. Господирует причина 1 (churn префикса).
