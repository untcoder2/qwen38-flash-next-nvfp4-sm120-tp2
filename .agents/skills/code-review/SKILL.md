# Ревью корректности кода

Результат — подтверждённые дефекты с местом, сценарием отказа и минимальным исправлением. Сам запрос на ревью не разрешает редактирование, сборку продукта, бенчмарк или деплой. Не изобретай находки ради объёма.

## Границы и исходное состояние

1. Прочитай действующие AGENTS.md и правила проекта. Уточни только недостающий объект проверки: рабочие изменения, ветка, PR, коммит или конкретные файлы.
2. Зафиксируй HEAD, статус индекса/рабочего дерева и рассматриваемый diff. HEAD не фиксирует незакоммиченные правки: перед итогом перечитай цитируемые участки в фактическом дереве.
3. Базу ветки получи из задания или существующих Git refs и их истории. Проверяй, что ref существует; не угадывай main или master. Если выбор базы неоднозначен, скажи это и запроси именно базу.
4. Читай полные затронутые функции и необходимые вызовы, типы, конфиги и пути очистки. Усечённый вывод дочитывай адресно; не делай вывод из одного hunk.

## Проверка

- Логика: ветвления, порядок, счётчики, возвращаемая форма, контракт ошибок, пустые/нулевые/большие значения, Unicode и границы.
- Ресурсы: файлы, сокеты, блокировки, отмена и очистка на всех выходах.
- Конкурентность: каждый read состояния сопоставь с write; проверь владельца, поколение, гонки и видимость между задачами.
- Глобальный флаг разрешений не должен давать соседней задаче права владельца. Для такой правки проверяй обе стороны: владелец допущен, конкурент отклонён.
- API и данные: аргументы, таймауты, игнорируемые ошибки, версии, кодировки, timezone, сериализация, точность и переполнение.
- Вывод модели и контент, из которого собирают промпт или конфиг, — недоверенный вход: трассируй как пользовательский вплоть до нисыка.
- Расхождения парсинга/нормализации между двумя компонентами (схема vs обработчик, парсер vs рантайм) — отдельный угол: допущение о поведении парсера подтверждай спекой или тестом, не интуицией.
- Отдельно отмечай полезные упрощения и пробелы проверок; стиль и необязательная чистка не блокируют исправление реального дефекта.

## Доказательство и отчёт

Для каждой находки: важность → file:line → конкретные вход/состояние → наблюдаемое или выводимое нарушение → минимальное исправление. Утверждение «проверки нет» подтверждай решающей веткой после прохода по вызываемым helper-функциям. Уже исправленный дефект не выдавай за текущий.

Разделяй доказанный анализ кода, выполненный воспроизводящий пример и непроверенную гипотезу. Отсутствие исполнимого стенда само по себе не отменяет прямое доказательство по коду; точно укажи, чего не проверял. Имена/значения секретов в доказательствах обезличивай.

Разделяй CORRECTNESS и QUALITY. Дедуплицируй одну причину, проявляющуюся в нескольких местах. Продюсерский кодекс [_shared/coding-discipline.md](${KIMI_SKILL_DIR}/../_shared/coding-discipline.md) — подсудность `D:*`: нарушение цитируется ID + file:line, как CWE. `D:PREMISE` без стоп-крана = FAIL; прочие `D:*` = FIX-FIRST, не блокер. Обязательна строка `discipline-audit:` с расхождениями самоотчёта coder'а (включая ok без доказательства и ok там, где строже n/a) — расхождение не гасится молча. Ясное и локальное, работающее без дефекта, не требует переписывания: «я бы сделал иначе» — не находка. Итог — строка `VERDICT: PASS|FAIL|FIX-FIRST (<N>)` в едином словаре гейта 18.10 (FIX-FIRST = не блокер, чинится в этой правке; данных не хватает — запроси вход, отдельного вердикта нет); границы покрытия и открытые вопросы — под строкой. PASS — результат ревью, а не разрешение на выпуск; перед коммитом/деплоем на бою обязателен гейт-парой ролей security-reviewer + code-reviewer (`.agents/agents/`), а не этим скиллом.

## Если исправления входят в задачу

Прочитай [общий цикл ревью](${KIMI_SKILL_DIR}/../_shared/review-cycle.md). Перед правкой выпиши инварианты. Для названных пользователем исправлений веди отдельные статусы; постороннюю чистку оставляй замечанием. Порядок source-review, компиляции и runtime-гейтов берётся из проекта; cargo check не заменяет компиляцию тестовых целей или проверку другой платформы.
